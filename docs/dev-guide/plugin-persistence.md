# Plugin 설정과 신뢰 기록의 파일 경계

`plugins.toml`은 비활성·builtin 제거 표시, 허가 권한, 명령별 단축키를 저장한다. `known-plugins.toml`은 공개 키와 미인증 선택을 기록한다. 두 파일 사이의 transaction은 없다. [Plugin 런타임](plugin-runtime.md)의 프로세스·세대 소유권은 저장 요청과 별도로 유지한다.

## 읽기·병합·교체

`tasty_host_plugin::file_persistence::ConfigUpdate`는 변경 전후의 소유한 값을 받는다. 실행할 때 공용 파일 잠금을 얻고 최신 문서를 다시 읽는다. 비활성·제거 표시는 ID별로, 권한은 토큰별로, 단축키는 plugin·명령별로 변경한 부분만 병합한다. 같은 명령의 단축키가 관측 이후 다르게 편집되었으면 충돌을 반환한다. 반환된 `PluginsConfig`는 요청 값에 최신 외부 변경을 합친 실제 확정 값이다. 활성화·권한 같은 명시적 명령은 cache에서 같은 값이어도 최신 파일에 적용한다. 이 명령 의도는 draft snapshot과 합치지 않는다.

신뢰 변경은 최신 DB를 잠금 안에서 수정하는 명령이다. 오래된 객체의 `save`는 같은 ID의 알려진 필드가 달라졌으면 충돌로 끝난다. 다른 ID와 알 수 없는 필드·섹션은 보존한다. 조건부 undo는 이 작업이 쓴 기록과 현재 기록이 일치할 때만 이전 값을 돌려놓는다. 이후의 신뢰 선택을 되돌리지 않는다.

파싱·읽기 실패를 빈 문서로 덮어쓰지 않는다. 로그와 후속 저장 오류에는 파서 원문을 넣지 않는다. 변경하지 않은 TOML 표현과 주석은 유지한다. 공용 `tasty_utils::file_replace`의 고유 임시 파일·원자 교체를 쓰며 새 파일은 Unix 0600으로 생성한다. 기존 파일의 권한·플랫폼 보안 메타데이터와 symlink는 공용 교체 계약을 따른다. 참여하지 않는 편집기의 변경은 교체 직전 fingerprint로 검사하며, 마지막 검사와 rename 사이의 경쟁까지 막지는 않는다.

## 호출부의 소유권

런타임은 소유한 파일 작업을 공용 writer에 제출한다. manager·registry guard를 worker에 넘기지 않는다. 파일 확정 뒤 메인 루프가 cache·권한·프로세스 효과와 원 호출자의 결과를 반영한다. 접수만으로 저장 성공이나 권한 허가를 알리지 않는다. 결과 불명은 명령을 다시 실행하거나 plugin을 시작할 근거가 되지 않는다. 파일 확정 뒤 manager 적용이 불가능해도 이미 저장한 결과와 앞서 끝난 비활성·삭제 효과는 오류 응답의 saved/applied/partial에 보존한다.

런타임의 보조 lifecycle 큐는 기존 64건 제한과 공용 writer 기본 바이트 한도로 접수한다. 큐의 동적 입력, coalescing draft, 활성 continuation과 아직 전달하지 않은 package·manifest 결과의 무게를 보유 기간 동안 계산한다. 이 무게는 보유 값의 추정치이며 RSS나 디렉터리 IO 양이 아니다. 새 입력·draft 확장이 한도를 넘으면 실행 전 거절하며 이미 접수한 실패 draft는 유지한다. 이미 생성된 큰 결과는 전달까지 계산하고 그동안 새 입력을 막는다.

단축키 draft는 아직 실행하지 않은 같은 구간의 변경만 합친다. 토글·설치·신뢰 명령은 순서를 지키는 경계다. 단축키 실패 값은 dirty로 남고, 나중에 성공한 변경은 자기 키의 실패 값만 해제한다.

GUI 부팅 worker의 builtin 설치는 동기 API를 사용할 수 있다. 파일 확정 뒤 discover/start로 이어야 하는 초기화 barrier이며 GUI 메인 루프에서 실행하지 않는다. 런타임 builtin 갱신은 파일 계획·복사와 메인 루프의 세대 회수·재시작을 나눈다. 파일을 바꾸지 않는 항목은 회수를 기다리지 않는다. 준비된 builtin 작업은 경로·매니페스트·서명 sidecar와 해당 plugin의 신뢰 관측을 보유하고, 회수 뒤 복사 전과 복사 뒤에 검증한다. 달라졌으면 권한·package·자동 재시작을 확정하지 않는다. 검증 범위는 기존 매니페스트 서명 정책을 따르며 바이너리 전체로 확장하지 않는다. 종료 중 생략한 재시작이나 이미 실행 중인 프로세스에 대한 no-op은 재시작 성공으로 보고하지 않는다.

재귀 디렉터리 삭제가 오류로 끝나면 일부 파일이 이미 삭제되었을 수 있다. 이 경우 디렉터리 결과는 unknown으로 보고하며 완료한 삭제나 삭제 개수를 추측하지 않는다. 아직 실행하지 않은 설정 저장의 saved=false와 앞서 완료한 비활성 효과는 별도로 보존한다.

## 메인 루프와 종료

GUI와 headless는 공용 file receipt, C1의 engine별 live effect, preset capture, L1 continuation, 설정 완료, 원 deferred 응답 순서로 수거한다. Observer 종료와 최종 file drain의 반환 회차에도 같은 순서를 지킨다. 구조 journal의 관측 대기 중에도 이미 접수한 파일 완료는 수거한다. retirement 대기만 기존 자식 회수 확인 주기로 독립 wake를 잡으며, worker receipt나 종료 후 Unknown에는 주기 wake를 만들지 않는다. continuation은 다음 파일 명령을 제출할 수 있으므로 완료 수거를 writer 종료와 같게 취급하지 않는다.

이 순서는 회차 안의 호출 순서만 보장한다. L1보다 먼저 끝난 receipt라도 그 수거 단계가 지나간 뒤 끝났다면 다음 회차에 수거된다. L1 continuation은 webhook·C1·preset 같은 다른 소비자의 수거 결과에 기대지 않는다. 기한 안에서 receipt는 유실되지 않고 원 응답은 drain 반환 전에 간다([종료 순서](../architecture/shutdown-sequence.md#파일-저장-완료와-원-요청-응답)).

종료 시작은 L1의 새 접수를 막는다. plugin 전체 종료 전에 manager를 유지한 채 접수된 다단계 작업을 진행하고, 같은 file writer drain 기한을 마지막 flush·join까지 이어 쓴다. 별도 기한을 새로 시작하지 않는다. 마지막 남은 수가 0이거나 기한을 넘긴 회차에도 receipt·continuation·원 응답을 순서대로 수거한다. 종료 중 enable·builtin 재시작은 수행하지 않는다.

기한이 지나면 아직 worker 결과를 확인하지 못한 명령과 미완료 retirement는 Unknown으로 원 호출자에게 한 번 응답한다. 앞서 확정한 저장·비활성·삭제 효과는 보존한다. 아직 시작하지 않은 큐 명령은 저장 전 거절로 응답하고 실행하지 않는다. 미확정 lifecycle 수는 별도로 남기며 writer 자체의 실제 join 관측으로 지우지 않는다. 이미 생성된 실패 단축키 draft도 미저장 상태로 남는다. 파일 명령은 자동으로 재실행하지 않는다.

## 검증 경계

호스트 크레이트의 파일 시험은 실제 잠금·외부 편집·실패·조건부 undo·주석·링크·mode를 다룬다. 이 시험만으로 GUI/headless의 공용 writer 주입과 종료 wiring을 증명하지 않는다. 실제 앱 검증은 격리된 데이터 루트와 소유한 가짜 plugin으로 저장 지연 동안 응답·프로세스가 대기하는지, 최종 응답과 종료 drain이 실제 receipt를 반영하는지 확인한다. Windows/macOS의 실행 여부는 Linux 검사 결과와 구분한다.
