# 국제화 (i18n)

모든 UI 문자열은 `t()` 계열을 통해 번역 키로 노출한다. 영어/한국어/일본어/중국어(간체)를 코드에 직접 하드코딩하지 않는다. 강제 정책은 [`../../CLAUDE.md`](../../CLAUDE.md) "국제화".

## API

번역 스토어는 leaf 크레이트 `tasty-i18n` 에 있다(전역 `OnceLock`). 본 바이너리는 `crate::i18n` 으로 재수출하고 `tasty-cli` 는 `tasty_i18n` 을 직접 의존 — **둘 다 같은 전역 테이블**을 공유한다.

```rust
pub fn t(key: &str) -> &str;                        // 단순 조회
pub fn t_fmt(key: &str, arg: &str) -> String;       // 모든 {}(또는 {0})를 같은 인자로 치환
pub fn t_fmt2(key: &str, a1: &str, a2: &str) -> String; // 인자 2개
pub fn t_args(key: &str, args: &[&str]) -> String;  // 인자 N개 (CLI 등 3+ 인자)
pub fn t_count(key: &str, n: u64, args: &[&str]) -> String; // 수 n 에 맞는 <key> / <key>_one 을 채움
pub fn t_count_template(key: &str, n: u64) -> &str;       // 수 n 에 맞는 템플릿을 채우지 않고 돌려줌
pub fn fill_args(template: &str, args: &[&str]) -> String; // 위 세 함수가 쓰는 채우기 규칙
pub fn t_fmt_fit(key: &str, fragment: &str) -> String;  // {} 1개 + 토스트 캡 맞춤
pub fn fit_fragment(fragment: &str, render: impl Fn(&str) -> String) -> String;
pub fn current_language() -> &'static str;
pub fn register_namespace(plugin_id: &str, lang_dir: &Path);
pub fn unregister_namespace(plugin_id: &str);
```

- **키를 못 찾으면 키 문자열을 그대로 반환** — 누락이 화면에 드러나 회귀를 즉시 노출.
- `t_fmt`는 모든 `{}`에 같은 값을 넣는다. `t_fmt2`와 `t_args`는 인자를 순서대로 한 번씩 넣는다.
- **자리표시 두 가지.** 한 번역문에는 둘 중 하나만 쓴다.
  - `{}` — 인자를 나오는 순서대로 하나씩 넣는다. 인자보다 `{}` 가 많으면 남은 `{}` 는 그대로 보인다.
  - `{0}` `{1}` … — 번호가 인자 순서다(0부터). 언어마다 어순이 달라 값의 순서를 바꿔야 할 때 쓴다. 같은 번호를 여러 번 써도 되고, 번호가 없는 인자는 보이지 않으며, 인자보다 큰 번호는 `{3}` 처럼 그대로 보인다. `t_fmt` 는 `{0}` 마다 같은 값을 넣는다.
  - en 이 `{}` 로 쓴 키를 ko 가 번호로 써도 된다. `"Moved {} of {}"` 와 `"{1}개 중 {0}개 이동"` 은 같은 두 칸을 받는다.
  - 섞은 문자열(`"{} {0}"`)은 런타임이 번호로 채우고 `{}` 를 그대로 둔다. 카탈로그 검사가 이런 값을 막는다.
  - 이스케이프 문법은 없다. 번호 자리표시를 쓰는 문자열에는 글자 그대로의 중괄호를 쓰지 않는다 — `{{0}}` 은 바깥 중괄호가 남고 안쪽 `{0}` 이 채워진다.
  - plugin SDK 번역기도 같은 구현(`tasty_i18n::fill_args`)으로 채운다. `Translator::t_fmt` 는 인자 하나, `t_args` 는 인자 여럿을 받고, 미리 읽어 둔 템플릿은 `tasty_plugin_sdk::i18n::fill_args` 로 채운다. 그래서 카탈로그 검사가 루트와 plugin `lang/` 에 같은 칸 규칙을 적용한다.
- **수를 받는 문자열은 `t_count` 로 읽는다(단수 규칙).** 영어는 1과 나머지가 갈리므로 수를 받는 en 키 `<key>` 마다 단수 변형 `<key>_one` 을 둔다(`"{} items"` / `"{} item"`). `t_count(key, n, args)` 는 `n == 1` 이고 변형이 있으면 그것을, 아니면 `<key>` 를 골라 `args` 를 위 규칙으로 채운다. 수 자체도 보이려면 `args` 에 넣는다.
  - ko·ja·zh-Hans 는 한 문자열로 충분해 변형을 두지 않는다. 변형은 자기 키와 같은 층(내장 언어 파일·사용자 override·언어팩·plugin `lang/` 파일)에서 온 것만 쓴다 — `<key>` 를 덮은 층이 `<key>_one` 을 주지 않으면 아래 층의 en 변형은 버린다. 그래서 ko 사용자에게 영어 단수 문장이 나오지 않는다.
  - 변형은 기준 키와 같은 인자 칸을 받는다. 수 자리도 남긴다(`"Copy {} item to {}"`) — `{}` 는 순서대로 채워지므로 수 자리를 빼면 뒤 인자가 앞으로 밀린다.
  - `_one` 으로 끝나도 기준 키(`_one` 을 뗀 키)가 카탈로그에 없으면 변형이 아니라 보통 키다.
  - 두 수를 한 문장에 받는 문자열(`"{} terminals, {} placeholders"`)은 변형 하나로 두 수의 단수를 함께 표현할 수 없다.
  - 수를 나중에 넣는 위젯에 템플릿을 넘길 때는 `t_count_template(key, n)` 으로 수에 맞는 템플릿만 받는다. 위젯이 수를 받기 전에 문구를 정해야 하면 `n` 이 1일 때와 아닐 때의 템플릿을 둘 다 넘긴다(`MultiSelectLabels::some_one`, 파일 선택기의 `hidden_folders_one`).
  - plugin SDK 도 같은 규칙이다(`Translator::t_count` · `Translator::t_count_template`, 변형 고르기는 `tasty_i18n::plural::pick`).
- **길이를 모르는 경로·실패 사유·OS 에러를 토스트에 넣을 때는 `t_fmt_fit`을 사용한다.** 번역 문장은 유지하고 인자 가운데를 생략한다. 길이가 허용 범위 안이면 그대로 둔다. `fit_fragment`에 직접 렌더 함수를 전달할 수도 있으며, 인자는 정확히 한 번 넣어야 한다. 인자에 최소 12자를 남기므로 번역 문장 자체가 188자를 넘으면 결과가 200자를 넘을 수 있다. 번역 문장에도 충분한 공간을 남겨야 한다. 이후 호스트의 `truncate_message`는 한도를 넘은 메시지 끝을 자르므로 식별에 필요한 경로나 오류 내용이 잘리지 않도록 주의한다.

```rust
ui.label(t("settings.appearance.custom_font_label")); // ✅
ui.label("Custom font file:");                         // ❌
```

## 번역 파일 위치

| 대상 | 경로 | 로드 |
|------|------|------|
| 본 바이너리 임베드 | `lang/{en,ko,ja,zh-Hans}.toml` (워크스페이스 루트) | 시작 시 `include_str!` |
| 번들/외부 plugin | plugin 디렉토리 `lang/{en,ko,ja,zh-Hans}.toml` | plugin 활성화 시 `register_namespace` |
| 사용자 오버라이드 | `~/.tasty/lang/{code}.toml` — **내장 코드(`en`/`ko`/`ja`) 전용** | 시작 시 내장 위에 overlay |
| 사용자 언어팩 | `~/.tasty/lang/<code>/pack.toml` (+ 동봉 폰트) — 내장이 아닌 새 코드 | 시작 시 영어 베이스 위에 overlay · 설정 콤보에 노출 |
| 사용자 plugin 오버라이드(내장 코드) | `~/.tasty/lang/plugins/<plugin-id>/<code>.toml` | plugin 설치본 en → 선택 언어 → 사용자 파일 |
| 사용자 plugin 오버라이드(새 코드) | `~/.tasty/lang/<code>/plugins/<plugin-id>.toml` | 같은 팩의 `pack.toml` 선택 후 위와 같은 순서 |

언어 선택은 `~/.tasty/config.toml` 의 `general.language`(내장 `en`/`ko`/`ja`/`zh-Hans` 또는 발견된 언어팩 코드), 변경 시 재시작. 오버레이 계층: **영어 베이스 → 선택 언어(내장 또는 팩) → 사용자 오버라이드(내장만)**, 누락 키는 한 단계 아래로 fallback. 내장 언어 파일은 모두 `[meta] name = "<표시 이름>"` 을 가진다 — 설정 콤보의 라벨 출처다. 코드는 정확히 일치해야 한다. `zh`·`zh-CN`·`zh_CN`·`zh-hans` 는 `zh-Hans` 의 별칭이 아니며 다른 미설치 코드처럼 영어로 돌아가고 경고 토스트를 낸다(설정 값은 그대로 둔다).

## 언어팩 (`~/.tasty/lang/<code>/pack.toml`)

내장 4 개 밖의 언어는 **디렉토리 + `pack.toml`** 이 하나의 언어팩이다. 로더·스캐너는 `tasty-i18n` 에 있고(`load_pack` / `scan_languages` / `available_languages`), 판정 근거·대안은 이 문서.

```toml
# ~/.tasty/lang/fr/pack.toml
[meta]
name = "Français"          # 콤보 표시 이름 (선택 — 없으면 코드 "fr" 가 라벨)

[font]                     # 필수 — 아래 넷 중 하나
builtin = true             # 내장 폰트 스택으로 충분
# file = "fonts/x.ttf"     # 팩 디렉토리 기준 상대경로 (동봉 폰트)
# family = "Noto Sans"     # 시스템 폰트 패밀리명
# candidates = ["fonts/x.ttf", "Noto Sans"]   # 순서대로 첫 성공

[button]                   # 나머지는 내장 lang 파일과 같은 키 트리
ok = "OK"
```

- **`[meta] name`** — 표시 이름. 공백뿐이거나 문자열이 아니면 없는 것으로 본다(코드 폴백). `meta.name` 키로 `t()` 조회도 된다.
- **`[font]`** — **필수**. 우선순위 `builtin = true` > `file` > `family` > `candidates`(섹션은 있는데 넷 다 없거나 빈 값이면 형식 오류). 선언을 실제 폰트 파일로 resolve 해 UI 폴백 체인에 붙이는 규칙은 아래 [`[font]` resolve 와 UI 폴백](#font-resolve-와-ui-폴백-체인)에 있다.
- 문자열 키는 `[font]` 를 제외한 모든 문자열 leaf. 영어 베이스 위에 overlay 되므로 일부만 번역해도 된다.
- 파일 크기는 `MAX_PACK_BYTES`의 2 MiB 상한을 적용한다. 팩·내장 override·사용자 plugin 파일이 대상이며 초과 파일은 파싱 전에 경고와 함께 제외한다.
- **빈 값(빈 문자열·공백뿐)은 번역이 없는 것으로 본다** — overlay 에서 빠져 아래 층이 그대로 보인다. 빈 값이 그대로 나가면 라벨 없는 버튼이 생기고 화면만 봐서는 어느 키가 비었는지 알 수 없다. `[meta] name` 과 `[font]` 의 문자열 검사(`non_empty_str`)와 같은 규칙이다. 로드 시 몇 개가 빠졌는지 `tracing::warn!` 로 알린다.
  - 모든 번역 overlay에 같은 규칙이 적용된다 — 팩 · 내장 오버라이드(`<builtin>.toml`) · plugin 언어파일(`<plugin>/lang/<code>.toml`)(이 문서). 근거가 파일 형상이 아니라 그 아래 층이기 때문이다 — 빈 값이 테이블에 도달하면 어느 경로든 라벨 없는 UI 가 되고 화면에 단서가 남지 않는다. **폴백 대상만 다르다**: 팩은 영어 베이스로, 오버라이드는 내장 `<code>.toml` 의 문구로, 설치 plugin 언어파일은 plugin 영어로, 사용자 plugin override는 직전 설치 언어로 돌아간다. `tasty-i18n` 단위 테스트가 세 경로에 같은 입력을 넣어 이 등가성을 고정한다.
  - 일부러 빈 텍스트를 두려면 **폭 없는 문자(U+200B ZWSP, U+2060)** 를 쓴다. **NBSP(U+00A0)·U+2007·U+3000 은 안 된다** — `str::trim` 은 유니코드 `White_Space` 속성을 전부 먹고 이 셋이 거기 포함된다.

### 발견 규칙 (설정 콤보 목록)

`available_languages()` = 내장 `en` / `ko` / `ja`(순서 고정) + `~/.tasty/lang/` 스캔 결과(코드순). 각 항목은 코드 · 표시 이름 · 출처(`Builtin` / `BuiltinOverridden` / `Pack`) · `[font]` 선언 종류 · 경로.

발견은 `load_pack` 이 아니라 **`load_pack_head`** 를 쓴다 — 목록에 필요한 것은 `[meta] name` 과 `[font]` 둘뿐인데, 문자열 leaf 를 전부 flatten 해서 만든 맵을 그대로 버리던 자리였다. 이 스캔은 설정 창을 처음 열 때 **렌더 스레드에서 동기로** 돈다. 수락/거절 판정은 두 경로가 동일하다("목록에 오르면 로드된다"가 성립해야 한다) — `tasty-i18n` 의 단위 테스트가 이 등가성을 강제한다.

| `~/.tasty/lang/` 안의 것 | 판정 |
|---|---|
| `<code>/pack.toml` (유효) | 팩 — 목록에 오른다 |
| `<code>/pack.toml` 파싱 실패 · `[font]` 없음/무효 | `tracing::warn!` + 제외 |
| `<code>/pack.toml` 이 2 MiB 초과 | 파싱 전 거부 — `tracing::warn!` + 제외 |
| `<builtin>/pack.toml` (예: `ko/`) | 내장 코드는 팩이 아니다 — warn + 제외 |
| `<builtin>.toml` (예: `ko.toml`) | 내장 오버라이드 — `ko` 가 `BuiltinOverridden` 으로 표시(`[meta] name` 이 있으면 라벨도 그것) |
| `<new>.toml` (예: `zz.toml`) | 팩이 아니다 — warn + 무시 (`zz/pack.toml` 로 옮겨야 한다) |
| `pack.toml` 없는 디렉토리 | 무시 |

### 부팅 시 로드와 폴백

`tasty_i18n::init(code)` 는 `LoadReport { requested, effective, outcome }` 를 돌려주고 `load_report()` 로 다시 읽을 수 있다.

- 팩이 정상이면 `effective == requested`.
- 팩이 **없거나**(`PackMissing`) **거부되면**(`PackInvalid` — 파싱 실패 · `[font]` 부재/무효 · 크기 상한 초과) 테이블은 **영어**(en 오버라이드 포함)로 만들고 `effective = "en"`. `current_language()` 와 자식 env `TASTY_LOCALE` 도 `en` 이다.
- 로드 시점에 `tracing::warn!` 한 줄(요청 코드 + 기대 경로 `~/.tasty/lang/<code>/pack.toml`, 단일 `<code>.toml` 이 놓여 있으면 그 사실도) — headless/CLI 는 이것이 전부다. 로그의 경로는 항상 온전하다.
- GUI 는 부팅 후 `LoadReport::user_warning()`(키 `i18n.warn.pack_missing` / `pack_invalid`)을 **경고 토스트 1회**로 띄운다. 토스트에는 본문 200자 캡이 있고(`tasty-i18n` 의 `TOAST_MAX_CHARS` — 호스트의 `truncate_message` 도 이 상수에서 파생하므로 캡은 한 곳에만 있다) 넘기면 호스트가 뒤를 자르고 `(200자 제한)` 접미를 붙이므로, `fit_path` 가 **경로만 가운데를 생략**해 캡 안에 맞춘다 — 머리와 꼬리(`<code>/pack.toml`)를 남긴다. 문구를 새로 쓰거나 번역할 때 이 캡을 염두에 두라: 문구가 길어질수록 경로에 남는 예산이 줄어든다.
- **설정값은 어느 경로에서도 고쳐 쓰지 않는다** — 사용자가 팩을 넣고 재시작하면 그대로 그 언어가 뜬다.

### `init` 전 조회

`init` 전에 부른 `t()`·`t_fmt()`·`t_fmt2()`·`t_args()` 는 **내장 영어 표**를 읽는다(`t_fmt_fit` 도 `t_fmt` 를 거친다).

- 이 표는 내장 `lang/en.toml` 만으로 만든다. 사용자 홈의 `lang/en.toml` 덮어쓰기는 읽지 않는다. 그래서 init 전 조회는 파일을 열지 않는다.
- 조회는 전역 저장소를 정하지 않는다. 뒤에 오는 `init(code)` 가 그대로 언어를 정한다. `current_language()` 는 `"en"` 이다.
- 표에 없는 키는 키 그대로 돌아온다. plugin namespace 는 `init` 전에 등록할 수 없으므로(`register_namespace` 는 경고 후 무시) plugin 키도 키 그대로다.
- 이렇게 하는 이유: 한 시험 프로세스에서 다른 시험의 `init("en")` 이 두 계산 사이에 끼어도, 그 앞뒤에서 계산한 문구가 같다. 시험 안의 `init` 이 모두 `"en"` 인 lib 시험 바이너리에서는 그린 문구와 기대 문구가 갈리지 않는다. `tasty-i18n` 의 `a_lookup_before_init_reads_the_same_english_as_an_english_init` 가 "init 전 조회 == 영어 init 뒤 조회" 를 고정한다.
- 남는 차이:
  - 영어가 아닌 언어로 `init` 하는 프로세스(실제 앱, 언어별 통합 시험)에서는 init 전 문구가 영어이고, 뒤 문구가 번역문이다.
  - 사용자 `en.toml` 덮어쓰기가 있으면 init 전 문구와 `init("en")` 뒤 문구가 다를 수 있다.

**`init` 누락 진단.** init 전 조회도 영어를 내므로 화면에 키가 보이는지로는 `init` 누락을 알 수 없다. 대신 프로세스에서 처음 일어난 init 전 조회를 `tracing::debug!` 한 줄로 남긴다: `i18n: '<key>' read before init — serving built-in English`.

- 보이는 곳: debug 빌드의 파일 로그(파일 출력이 켜진 뒤의 조회만 남는다) 또는 `TASTY_LOG=debug` 로 띄운 stderr. release 의 파일 로그는 warn 이상이라 남지 않는다.
- 프로세스당 첫 조회 하나만 남기므로, 어느 경로들이 init 전에 읽는지 전부 보이지는 않는다.

### 설정 콤보 동작

Settings › General 의 언어 콤보는 위 목록만 보여 준다(`tasty_ui_widgets::language_select`, 갤러리 Settings specimen 과 같은 위젯). 라벨은 `[meta] name`, 없으면 코드. 현재 설정값이 목록에 없으면(팩이 지워진 뒤 등) 값을 덮어쓰지 않고 `"<code> (not found)"` 행(`settings.general.language_missing_suffix`)을 끝에 붙여 선택 상태로 유지한다 — 그 행을 다시 골라도 값은 변하지 않는다. 목록은 설정 창을 열 때 1회 스캔한다.

### `[font]` resolve 와 UI 폴백 체인

셸 UI 폰트 폴백 체인은 기본이 **egui 기본 폰트(라틴 중심) + 시스템 CJK 폰트**다(Monospace 와 이름 family 는 번들 D2Coding 이 맨 앞). 아랍·히브리·태국·데바나가리처럼 그 밖의 스크립트는 글리프가 없어 □(tofu)로 뜬다. tasty 는 스크립트별 폰트를 **찾아주지 않는다** — 언어팩이 `[font]` 로 선언하고, tasty 는 그 선언을 resolve 해서 체인 **맨 뒤**에 붙이는 것만 한다(폰트 동봉·라이선스는 팩 제작자 책임).

**시스템 CJK 폰트** — 후보 목록은 `tasty_egui_theme` 한 곳에 있고, 본체·갤러리·plugin 넷이 같은 `install_system_cjk_fallback` 으로 설치한다. `plugin_locale_font_call_convention` 이 다른 소스에 현재 후보의 파일 이름이 다시 적히면 실패한다(검사에 적어 둔 이름만 찾으므로 후보를 추가하면 검사의 목록도 고친다). OS마다 칸(slot) 목록이 있고 칸마다 후보 순서대로 파일을 읽어 `tasty_i18n::font::validate_face` 를 통과한 첫 글꼴 하나를 쓴다. 칸이 여럿이면 칸 순서대로 체인에 붙는다(키 `system_cjk`, `system_cjk_2`). 없는 파일은 말없이 넘어가고 판정에 걸린 파일은 경고하고 넘어간다. 모든 칸이 실패하면 경고를 남기고 해당 글자는 □ 로 나온다. 칸 순서는 `std::env::consts::OS` 값으로 고르는 순수 함수라 다른 OS의 표도 시험에서 읽는다.

| OS | 칸(순서대로) | 글꼴 번호 |
|---|---|---|
| Linux | 칸 하나: `NotoSansCJK-Regular.ttc`(`/usr/share/fonts` 아래 Debian·Ubuntu, Arch, Fedora 이전 경로 등 5곳), `NotoSansCJK-VF.ttc`(Fedora 가변 글꼴) | `zh-Hans` UI는 파일에서 이름으로 찾은 `Noto Sans CJK SC`. 그 밖의 언어는 0번(`NotoSansCJK-Regular.ttc` 에서 측정한 결과 JP) |
| Windows | `zh-Hans` UI: `msyh.ttc` → `malgun.ttf`. 그 밖의 언어: `malgun.ttf` → `msyh.ttc` | `msyh.ttc` 는 이름으로 찾은 `Microsoft YaHei UI`(1번), `malgun.ttf` 는 0번 |
| macOS | `zh-Hans` UI: 간체 칸 → 한글 칸. 그 밖의 언어: 한글 칸 → 간체 칸. 간체 칸은 `Hiragino Sans GB.ttc`, 없으면 `STHeiti Light.ttc`. 한글 칸은 `AppleSDGothicNeo.ttc`, `ヒラギノ角ゴシック W3.ttc`, `Arial Unicode.ttf` 순서 | 간체 칸은 이름으로 찾은 `Hiragino Sans GB`(0번, W3), STHeiti면 `Heiti SC`(1번). 한글 칸은 0번 |

- **언어**: 호스트가 부팅 때 정한 `TASTY_LOCALE` 을 읽으므로 본체와 plugin 이 같은 글꼴 번호를 고른다. 언어 변경은 재시작 뒤 반영된다.
- **`zh-Hans` 만 글꼴 번호를 바꾸는 이유**: 묶음 안의 지역 글꼴은 공용 한자를 다르게 그린다(GB2312 1급 3,755자 중 JP와 SC의 글리프가 다른 글자 1,662자). 다른 언어의 번호를 바꾸면 기존 사용자의 한자 형태가 바뀐다. 각 지역 글꼴은 한글·가나·간체를 함께 가지므로(Noto Regular의 0번·2번에서 GB2312 1급, 한글 11,172자, 가나 측정) Noto 묶음을 쓸 때는 어느 언어에서도 언어 이름과 파일 이름이 □ 로 나오지 않는다.
- **Windows가 파일 둘을 쓰는 이유**: Windows 11 기본 설치(간체 보충 글꼴 기능 미설치, 2026-11-10 측정)에서 맑은 고딕(`malgun.ttf`)은 GB2312 1급 3,755자 중 1,400자가 없고(`简体中文`의 `简` 포함) 공용 한자를 JP·KR 형태로 그린다. `msyh.ttc` 의 Microsoft YaHei UI는 GB2312 1급과 가나를 모두 갖고 SC 형태지만 한글이 없다. 그래서 `zh-Hans` UI는 YaHei를 앞에 두어 공용 한자를 SC 형태로 그리고 한글만 맑은 고딕으로 채운다. 그 밖의 언어는 맑은 고딕을 앞에 두어 기존 한자 형태를 유지하고 맑은 고딕에 없는 간체만 YaHei로 채운다. 글꼴을 쓰는 프로세스마다 두 파일을 함께 읽는다(`msyh.ttc` 19,704,352바이트, `malgun.ttf` 13,459,196바이트). 호스트는 글꼴 정의를 부팅, surface 글꼴 갱신, 설정 창 미리보기마다 다시 만든다. 그래서 시스템 CJK 파일은 판정을 통과하면 경로별로 한 번만 읽어 프로세스가 끝날 때까지 두고, egui에 정적 수명의 빌린 바이트(`FontData::from_static`)로 넘긴다. 공유하지 않으면 정의를 만들 때마다 파일 사본이 생기고, 소유한 바이트(`from_owned`)로 넘기면 epaint가 글꼴 캐시를 만들 때마다 다시 복사한다. 없는 파일과 판정에 걸린 파일은 두지 않고 다음 호출에서 다시 읽는다. 설정 창을 연 debug 호스트에서 잰 값은 Windows `WorkingSet64` 283,766,784~285,589,504바이트, Linux `VmRSS` 410,592~440,032 kB다(zh-Hans·en 각 2회, 2026-11-10). 번들 플러그인의 메모리는 재지 않았다. `simhei.ttf`·`Deng.ttf` 는 기본 설치에 없다.
- **macOS가 파일 둘을 쓰는 이유**: macOS 27.2(2026-11-10 측정)의 `AppleSDGothicNeo.ttc` 0번은 GB2312 1급 3,755자 중 1,669자가 없고(`简体中文`의 `简`·`体` 포함) 공용 한자를 KR 형태로 그린다. `/System/Library/Fonts/Hiragino Sans GB.ttc` 의 0번(W3)은 GB2312 1급과 가나 176자를 모두 갖고 SC 형태지만 한글이 없다. 그래서 Windows와 같은 방식으로 `zh-Hans` UI는 Hiragino Sans GB를 앞에 두고, 그 밖의 언어는 Apple SD Gothic Neo를 앞에 두어 기존 한자 형태를 유지한다. 간체 칸은 후보 파일마다 글꼴 이름이 달라 칸의 이름 목록(`Hiragino Sans GB`, `Heiti SC`)을 앞에서부터 찾는다. `STHeiti Light.ttc` 의 0번은 TC다. 한글 칸의 두 번째 후보 `ヒラギノ角ゴシック W3.ttc` 에는 한글이 없고, `Arial Unicode.ttf` 는 한글·간체를 모두 갖지만 공용 한자가 SC 형태가 아니다. PingFang SC는 SC 형태이지만 `PingFang.ttc` 가 MobileAsset 저장소의 해시 이름 폴더에 있어 정적 경로로 찾을 수 없고, 시스템 UI용 `PingFangUI.ttc` 는 private framework 경로이며 `hvgl` 윤곽만 있어 쓰지 않는다. 두 칸을 쓰는 debug 호스트의 RSS는 254~258 MiB다(3회, 2026-11-10). `Hiragino Sans GB.ttc` 23,510,656바이트를 함께 읽는다. 번들 플러그인의 메모리는 재지 않았다. 11.0~26 등 다른 macOS 버전의 파일 유무는 재지 않았다.
- **가변 글꼴의 굵기**: `NotoSansCJK-VF.ttc` 는 `wght` 기본값이 100이고 egui 는 축을 지정하지 못해 Thin 으로 그린다. 고정 글꼴이 없을 때 □ 대신 쓰는 마지막 후보다.
- **Monospace의 한계**: D2Coding 이 앞에 있어 D2Coding 에 있는 한자(GB2312 1급 중 2,086자)는 D2Coding 으로, 없는 한자는 시스템 CJK 폰트로 나온다. 번역 문구를 그리는 작은 라벨은 이 체인을 쓰지 않고 `font-label`을 읽어 `ja`·`zh-Hans`에서 Proportional로 그린다(아래 "라벨 글꼴"). 고정폭으로 남는 값(경로·코드·ID)과 `Input mono`의 자리표시 글자에는 글꼴이 섞일 수 있고 SC 형태가 보장되지 않는다. 터미널 본문은 이 체인을 쓰지 않으며 cosmic-text 대체 경로를 따른다.

**라벨 글꼴** — 번역 카탈로그의 낱말을 그리는 작은 라벨(절·열 제목, Tag, 상태 낱말, 낱말이 든 개수, 단위, 힌트)은 `tasty_ui_widgets::label_font` 또는 `label_font_family`를 읽는다. 값은 UI 언어로 정하고 문자열별로 고르지 않는다. 언어 코드의 첫 부분이 `ja`·`zh`면 Proportional 체인의 글자를 같은 크기 Monospace의 행 높이와 baseline으로 그리고(`MONO_LINE_SANS_FAMILY`, [의존성 이슈](dep-issues.md)), 그 밖은 Monospace다. 라틴은 Ubuntu-Light 그대로이며 본문 UI sans는 움직이지 않는다. 이 체인의 글꼴 순서는 Proportional 체인(Ubuntu-Light, NotoEmoji, emoji-icon-font, 시스템 CJK, 언어팩 글꼴) 뒤에 Monospace 첫 글꼴이 붙는 것이다. 본체와 갤러리에서는 그 글꼴이 D2Coding이라, 시스템 CJK 글꼴에 없는 `ー`와 상태 글리프가 □가 되지 않는다. 번들 플러그인은 D2Coding을 설치하지 않아 egui 기본 Monospace 글꼴이 붙는다. 값은 부팅 때 정해진 `TASTY_LOCALE`이다. 번들 플러그인은 `tasty_i18n::init`을 부르지 않아 `current_language()`가 항상 `en`이므로 이 값을 읽는다. 언어 변경은 재시작 뒤 반영되므로 프로세스마다 한 번 읽는다. 값(경로·ID·버전·크기·시각·포트·단어 없는 숫자·키캡)은 모든 언어에서 Monospace이며 값을 담은 Tag는 `tag_mono`를 쓴다. 번역 문자열 안의 값은 낱말과 함께 라벨 글꼴을 따르고, 값이 고정폭이어야 하면 run을 나눈다. 대조 검사는 [중복 목록 관리](duplicated-sets.md#라벨-글꼴의-언어-집합)에 있다.

**resolve 규칙** — `[font]` 네 형태가 tasty 가 아는 전부다(`src/boot/locale_font.rs`):

| 선언 | resolve | 실패 |
|---|---|---|
| `builtin = true` | 아무것도 붙이지 않는다(라틴 팩용) | — |
| `file = "fonts/x.ttf"` | 팩 디렉토리 기준 상대경로. 글꼴 묶음 파일이면 0번을 읽는다. **팩 밖으로 벗어나는 경로**(절대경로·`..` 상위 참조)는 거부한다 | 파일 없음/거부 → 경고 |
| `family = "Noto Sans Arabic"` | 시스템 폰트 DB 에서 그 패밀리를 **파일로** 가진 face 의 경로와 글꼴 번호(`tasty_font::FontConfig::family_source_path`) | 미설치/파일 아님 → 경고 |
| `candidates = [...]` | 각 항목을 **"경로처럼 보이면 `file`, 아니면 `family`"** 로 순서대로 시도, 첫 성공 | 전부 실패 → 경고 |

- **`candidates` 의 file/family 판별**: 항목이 `/`·`\` 를 담거나 `.ttf`·`.otf`·`.ttc` 로 끝나면 파일 경로(팩 상대), 아니면 시스템 패밀리명으로 본다.
- **붙이기 전 검증**: resolve 한 파일은 append 하기 전에 `ab_glyph`(epaint 가 쓰는 파서)로 파싱하고 줄 높이가 0보다 큰지 확인한다. 파싱에 실패하거나 줄 높이가 0 이하인 언어팩 폰트는 거절한다. egui 는 파싱에 실패한 폰트에서 복구 경로 없이 panic 하고(epaint 0.31.1 `text/fonts.rs:210`), 줄 높이가 0 이하인 폰트는 파싱을 통과한 뒤 글자를 처음 배치할 때 panic 한다(`text/font.rs:94`). 언어팩 폰트는 Proportional·Monospace 양쪽에 붙고 egui가 첫 pass에서 글리프를 미리 읽으므로 UI가 나오기 전 부팅 첫 프레임에서 panic 한다. 그래서 부팅 단계에서 먼저 거른다. 이 판정은 파일 안의 다른 표까지 확인하지 않는다. `glyf`가 손상되거나 `cmap`이 없는 파일은 통과하고, 측정에서 panic 없이 해당 글자가 비거나 다음 폰트로 넘어갔다. 이 판정은 위 두 조건만 거른다. 글리프가 texture atlas보다 큰지는 글자 크기와 배율에 달려 있어 파일로 판정할 수 없으므로, 그런 글자는 패치한 epaint 사본이 그릴 때 비운다([`vendor/epaint/PATCHES.md`](../../vendor/epaint/PATCHES.md)). 글꼴은 계속 쓰인다. 본체는 경고 로그를 남기고, `-p`로 빌드한 번들 플러그인은 epaint의 `log` feature가 꺼져 경고를 남기지 않는다. 판정은 `tasty_i18n::font::validate_face`(글꼴 번호 지정, `validate` 는 0번) 한 함수이고 파일 읽기와 판정을 묶은 것이 `read_validated`다. egui 가 읽을 글꼴 번호와 같은 번호로 판정한다. 부팅 resolve와 append 지점(`tasty_egui_theme::install_locale_font_fallback`)이 `read_validated`를 함께 사용하며, append는 검증한 바이트 자체를 egui에 넘긴다. 렌더러 없이 언어팩 제작 검사에서도 같은 함수를 사용할 수 있다. 설정의 기본·플러그인 `custom_font_path`와 이름으로 찾은 글꼴, 시스템 CJK 폰트도 같은 판정을 쓰지만 저장은 막지 않고 사용할 때 건너뛴다. 터미널 글꼴은 이 판정을 쓰지 않고 cosmic-text에서 그려 보는 판정을 쓴다([설정](../features/settings/index.md)).
- **부팅 1회 resolve · 결과 보관**: resolve 는 `src/boot/locale.rs` 의 `locale::init` 에서 1회 수행하고 결과 절대경로와 글꼴 번호를 `ResolvedLocale` 의 `font_file`·`font_face` 에 담는다. 두 호스트 폰트 셋업 경로가 같은 값을 읽고, 자식 plugin 프로세스에는 `TASTY_LOCALE_FONT=<절대경로>`, `TASTY_LOCALE_FONT_FACE=<번호>` env 로 전달한다(없으면 둘 다 unset — `crates/tasty-host-plugin/src/process.rs` 가 propagate). `family`/`candidates` 로 찾은 시스템 폰트도 **호스트가 resolve 한 파일 경로**를 넘겨 plugin 이 다시 DB 를 뒤지지 않게 한다.
- **혼합 렌더(마지막 폴백)**: CJK 와 같이 체인 맨 뒤에 붙으므로 라틴 글리프는 기본 폰트, 팩 스크립트만 팩 폰트로 렌더된다. "전부 팩 폰트" 는 범위 밖이다(후일 `priority` 옵션).
- **소비처**: 셸 UI 두 경로(`src/gfx/gpu/fonts.rs` 의 `setup_egui_fonts`, `src/adapters/ui/font_registry.rs` 의 `build_font_definitions`)와 egui UI 를 그리는 plugin 넷(`crates/tasty-plugin-{clipboard-viewer,git-viewer,image}/src/main.rs`, `crates/tasty-plugin-markdown/src/popup.rs`)이 **모두 같은 `install_locale_font_fallback` 헬퍼**를 CJK 뒤에서 부른다 — 검증(ab_glyph)이 곧 "어떤 폰트를 거부하는가" 라는 판정이라, 사본을 두면 host 는 받고 plugin 은 거부하는 갈림이 생긴다. 그래서 plugin 도 `tasty-egui-theme` 을 직접 의존해 같은 판정기를 쓴다.
- **실패는 폴백 없이 경고만**: resolve/검증에 실패하면 문자열 자체는 그대로 로드되고(해당 스크립트는 □) UI 폰트만 안 붙는다. headless/CLI 는 `tracing::warn!`, GUI 는 부팅 후 경고 토스트 1회(팩 폴백 토스트와 같은 구조).
- **RTL(아랍·히브리)은 범위 밖**: egui 는 양방향 텍스트를 지원하지 않아, 글리프가 붙어도 어순이 깨진다. `[font]` 는 글리프 유무만 해결한다.

## 새 문자열 추가 절차

1. 코드에 `t("namespace.key")` 호출 먼저 추가.
2. `lang/en.toml`·`ko.toml`·`ja.toml`·`zh-Hans.toml` **네 파일 모두** 같은 키 추가. (누락 시 fallback 영어 or 키 노출.)
3. plugin 문자열이면 그 plugin 의 `lang/` 에 추가.
4. `cargo test --locked --test i18n_key_parity` 와 `cargo test --locked -p tasty-doc-guards --test no_hardcoded_ui_strings` 로 확인 — 네 파일 정합과 하드코딩 여부를 [강제 테스트](#강제-테스트) 가 잡는다.

키 네이밍: `<영역>.<서브영역>.<항목>` (점 계층, 예: `settings.appearance.theme_label`).

| 언어 | 종결 | 예 |
|------|------|-----|
| en | 평서문 · 명령형 그대로 | `It may have been deleted. Pick another from the header.` |
| ko | 존댓말 `~합니다` / 권유는 `~하세요`. 평서형 `~한다` · 하라체 `~하라` 금지 | `삭제되었을 수 있습니다. 헤더에서 다른 DAG 를 선택하세요.` |
| ja | ですます체. 常体(`~する` / `~ない` / `~選ぶ`) 금지 | `削除された可能性があります。ヘッダーから別の DAG を選択してください。` |

- **명사구는 규칙 밖이다** — 버튼 · 라벨 · 컬럼 헤더 · 빈 상태 제목처럼 종결어미가 없는
  문자열은 그대로 둔다(`닫기` / `DAG 없음` / `閉じる`).
- **프로젝트 문서의 문체를 lang 파일로 가져오지 않는다.** `CLAUDE.md` 와 `docs/` 는
  `~한다` 체를 쓰지만 UI 문자열은 사용자에게 말을 거는 자리라 화자 태도가 다르다.

## UI 문장 안의 CLI 조각

UI 글꼴은 하이픈 두 개를 대시 하나처럼 이어 그린다. 그래서 egui가 그리는 UI 문장 안의 CLI 명령·옵션·인자는 내장 언어 파일 모두에서 백틱으로 감싼다(`` `--webhook-port` ``, `` `tasty webhook list` ``).
옵션 글자는 바꾸지 않으므로 사용자가 그대로 따라 입력할 수 있다. 그리는 쪽은 `tasty_ui_widgets::ui_copy`, 또는 painter로 직접 그리는 곳에서는 `ui_copy_job`·`paint_ui_copy`를 쓴다.
이 위젯은 백틱 구간을 문장과 같은 크기의 mono code run으로 그리고 run 안에서는 줄을 바꾸지 않는다. 가운데 정렬 문장은 `center_ui_copy_rows`로 줄마다 가운데에 옮긴 뒤 그린다. 토스트 카드처럼 surface-raised 용기 위의 문장은 `UiCodeContainer::Raised`로 그려 run 채움이 용기와 같은 색이 되지 않게 한다.
모양은 [디자인·갤러리 매핑](../design/systems/design-gallery-mapping.md#ui-code-components)의 ui-code 절을 따른다.

| 표면 | 키 |
|------|----|
| 부팅 오류 화면의 본문·안내 | `boot.webhook_port.hint_argument` · `boot.webhook_port.hint_config` 등 `BootErrorInfo`로 넘기는 문구 |
| 토스트 본문 | `i18n.warn.pack_missing` 등 토스트로 띄우는 문구 |
| 알림 본문 | `webhook.warn.*`. 알림 항목은 code run을 그리지 않아 백틱이 글자 그대로 보이며, `notification.list` 응답에도 그대로 실린다 |
| DAG 빈 화면 안내 | `dag.empty.none_hint` |

- 같은 문구를 표준 오류·로그에도 남기면 그쪽에는 백틱이 글자 그대로 나간다.
- OS 메시지 상자(`boot.webhook_port.differs*`)처럼 egui 밖에서 그리는 문구는 run을 그릴 수 없으므로 백틱을 넣지 않는다.
- 안내 모달(`info_modal`)의 `` `명령` `` 칩은 별도 디자인을 따르며 이 규칙과 크기가 다르다.

## OS 네이티브 표면

egui 밖의 OS 네이티브 UI 도 사용자 표면이라 예외가 아니다. 라벨은 전부 `t()` 이고 단축키(key equivalent)는 별도 정책([key-mapping](../design/policies/key-mapping.md))이라 서로 독립이다.

| 표면 | 키 | 코드 |
|------|----|------|
| macOS 메뉴바(NSMenu) + Dock 메뉴 | `menu.macos.*` | `crates/tasty-platform/src/macos_delegate.rs` |
| 시스템 트레이 메뉴·툴팁(3 OS) | `tray.*` | `crates/tasty-platform/src/system_tray.rs` |
| Windows 작업표시줄 Jump List | `jump_list.*` | `crates/tasty-platform/src/jump_list.rs` |

- 앱 이름을 결합하는 macOS 항목(About / Hide / Quit)은 키 값에 `{}` 를 두고 `t_fmt(key, &process_name)` 로 채운다 — 언어별 어순("About Tasty" / "Tasty 가리기" / "Tastyを非表示")을 리터럴 결합으로는 맞출 수 없다.
- ko·ja·zh-Hans 의 macOS 메뉴 값은 OS 표준 메뉴 관용 표기(Apple 용어집)를 따른다 — 옆에 놓이는 다른 앱 메뉴와 같은 말을 써야 한다.
- Windows `w!()` 는 컴파일 타임 리터럴이라 번역 문자열에 쓸 수 없다 — 런타임에 null-terminated `Vec<u16>` 로 만들어 `PCWSTR` 로 넘기고, 호출이 끝날 때까지 버퍼를 살려 둔다. 실행 인자 토큰(`"new-window"`)만 `w!()` 로 남는다.
- 모든 호출 지점은 `locale::init()` 이후(macOS delegate 주입 / `resumed()`)라 부팅 순서 문제는 없다.

## Plugin 네임스페이스

활성화 시 `register_namespace(plugin_id, &lang_dir)` 로 overlay 합류. 전체 기동(`discover_and_start`)은 발견한 모든 패키지를 비활성 여부와 관계없이 등록하고, 헤드리스의 kind·namespace 요청처럼 플러그인 하나만 시작하는 `start_one_enabled` 는 시작 전에 그 패키지를 등록한다. 호스트가 그 플러그인의 문자열로 기본 탭 이름 같은 값을 저장하기 전에 번역이 준비돼야 하기 때문이다. 저장된 값은 나중에 등록돼도 다시 번역되지 않는다. 키 충돌 방지를 위해 plugin 은 자기 키를 `<plugin_id>.<...>` 로 prefix 한다. 비활성/제거 시 `unregister_namespace` 로 정리. (문자열은 `Box::leak` 으로 `&'static` 을 만족 — 활성화 빈도가 낮아 누수는 무시할 수준.)

위 네임스페이스는 **host 가 그리는** plugin 문자열(매니페스트 `*_i18n_key` 등)용이다. plugin 이 **자기 프로세스에서 직접 그리는** 문자열은 host 카탈로그에 닿지 못하므로, SDK `tasty_plugin_sdk::i18n::Translator` 가 plugin 의 `lang/` 을 직접 로드한다(base `en.toml` → 활성 언어 overlay, 키 미스 시 키 반환 — host 와 같은 규칙). 활성 언어는 `TASTY_LOCALE` env 로 받는다.

- `TASTY_LOCALE` 은 host 본 바이너리가 부팅 시 `general.language` 에서 확정해 **자기 프로세스 env 에 set** 하고(`src/boot/locale.rs` — 이벤트 루프·스레드 생성 전 단일 스레드 구간), host-plugin 이 spawn 시 그대로 propagate 한다(`crates/tasty-host-plugin/src/process.rs` — `tasty-i18n` 비의존). 셸에서 export 한 값은 설정에 덮인다 — env 만으로 plugin 언어를 임시로 바꾸는 우회는 없으므로, 언어를 바꿔 보려면 `general.language` 를 편집하거나 debug 빌드에서 `tasty debug settings apply --json '{"general":{"language":"ja"}}'` 로 바꾼 뒤 재시작한다.
- 언어팩 폰트가 resolve 되면 `TASTY_LOCALE_FONT`(절대경로)와 `TASTY_LOCALE_FONT_FACE`(글꼴 번호)도 같은 경로로 전달된다. 폰트가 없으면 둘 다 unset.
- Codex 세션 helper(`tasty-plugin-codex session`·`terminal`)는 플러그인 프로세스가 아니라 터미널 셸의 자식이다. plugin env가 없어 `Translator::from_plugin_env` 대신 셸이 물려받은 `TASTY_LOCALE`과 `TASTY_PARENT_HOME`으로 같은 번역 층을 읽는다. OS 로케일(`LANG`)은 보지 않고, `TASTY_LOCALE`이 없거나 비면 `en`이다. 그 셸에서 사용자가 `TASTY_LOCALE`을 직접 바꾸면 helper는 바꾼 값을 따른다.
- helper는 `TASTY_PARENT_HOME`이 절대경로일 때만 사용자 번역을 읽는다. 터미널 셸은 host의 `TASTY_HOME`을 그대로 넘기므로, host를 상대 `TASTY_HOME`으로 실행하면 helper 문구에는 사용자 번역이 빠지고 설치본 번역이 나온다. 작업 폴더 아래 같은 상대 경로의 파일은 읽지 않는다.
- 값은 spawn 시점 고정이다 — 언어 변경은 재시작 후 plugin 에 반영된다(host 자신과 같은 정책). 근거·대안: 이 문서.

host-plugin을 별도 테스트나 다른 호스트에서 사용할 때 locale env가 없으면 en으로 둔다. 폰트 env가 없거나 비어 있으면 자식에서도 제거해 이전 값을 전달하지 않는다. 부팅 뒤에는 프로세스 env를 다시 쓰지 않는다. 이 순서가 바뀌면 env 갱신의 단일 스레드 조건도 다시 확인한다.

### 사용자 plugin 번역

host의 `register_namespace`와 SDK의 `Translator::from_plugin_env`는
`tasty_i18n::plugin_catalog::load`를 함께 호출한다. 설치본 `en.toml` → 설치본
`<code>.toml` → 위 표의 사용자 파일 순서이며, 빈 overlay 값은 직전 층을 유지한다.
사용자 파일은 본체와 같은 2 MiB 상한·TOML 파서를 쓰고, 잘못된 파일은 경고 후
무시한다. 파일이 없으면 설치본 번역을 쓴다. 키는 plugin이 실제 쓰는 이름 그대로다
(예: `clipboard_viewer.popup.title`); 경로의 ID는 매니페스트 ID(`com.tasty.clipboard-viewer`)다.

host는 초기화할 때의 언어 디렉터리를 보관한다. 상대 `TASTY_HOME`은 자식 환경을
조립할 때 host CWD 기준 절대경로로 확정하여 `TASTY_PARENT_HOME`에 전달한다.
파일 존재를 요구하는 canonicalize는 하지 않으며, 절대경로 확정 실패는 spawn 오류로
전달한다. plugin CWD 아래 같은 상대 파일이 있어도 host의 파일을 읽는다. SDK는 `TASTY_PARENT_HOME/lang`만
사용하고 값이 없거나 비면 사용자 overlay를 읽지 않는다. SDK 프로세스의 `TASTY_HOME`
또는 작업 디렉터리로 폴백하지 않는다. plugin ID는 기존 매니페스트 문법과 정상 경로
컴포넌트, 언어 코드는 기존 언어팩 문법으로 제한한다. 이 검사는 파일명 경계이며
OS sandbox나 심볼릭 링크 격리를 제공하는 것은 아니다. 기존 권한은 host IPC 권한이라
SDK의 자기 번역 파일 읽기에 새 grant가 필요하지 않다([plugin-permissions](plugin-permissions.md)).

번역 변경 적용은 재시작이다. host의 본체 카탈로그 우선 조회는 유지되므로 plugin 전용
키를 본체 override/pack에도 중복해서 넣지 않는다. plugin 번역은 위 plugin 파일에
모은다. 설치 디렉터리는 고치지 않아 업그레이드 후에도 사용자 파일이 보존된다.
### plugin 이 돌려주는 IPC 에러 문구

**번역한다.** JSON-RPC `error.message` 는 CLI 가 stderr 로 그대로 흘리는 사용자 표면이다.

플러그인이 만든 오류 문구는 해당 플러그인의 번역기로 작성한다. 기계 처리는 `code`로 분기하며 번역된 `error.message`를 파싱하지 않는다. CLI가 서버 오류를 번역하지 않는 규칙과 다르다. CLI는 이미 만들어진 문구를 그대로 전달한다.

**예외 하나 — `*.hook` 은 두 곳으로 나간다.** `tasty <plugin> hook …` 의 실패는 stderr
말고 `~/.tasty/hook-failures.log` 에도 실리는데, 그 파일은 에이전트가 `grep` 으로 읽는
로케일 무관 채널이다(아래 "하드코딩 허용 예외"). **그 줄에서 언어에 상관없이 읽는 부분은
구조화된 필드(`method`/`event`/`surface`/`code`)이고 `reason` 산문은 그 문구를 만든 쪽의
언어를 따른다** — 그러므로 여기 문구를 번역하는 것이 그 채널의 계약을 깨지 않는다.
근거·대안·재검토 조건은 [CLI 크레이트 내부 구조 — 세 갈래 대칭](cli-structure.md).

## CLI 출력 문자열

`tasty <subcommand>` 의 client 모드는 본 바이너리와 **같은 프로세스**에서 돌아(부팅 시 `locale::init()`), GUI 와 동일한 번역 테이블을 쓴다. `locale::init()` 은 라우팅 판정(`cli_routing::parse_or_route`) 진입부에서 올라가므로, clap 파싱 전에 도는 plugin CLI fallback(`tasty <plugin 명령>`) · `-a` · root `-h` 경로의 stderr 도 번역된다. `tasty-cli` 에서 `tasty_i18n::{t, t_fmt, t_args}` 를 직접 호출한다.

- 키 prefix 는 `cli.<명령>.<항목>` (예: `cli.remote_check.not_found`).
- 인자 3+ 메시지는 `t_args(key, &[...])`.

### CLI 도움말 (clap `about` / `help`)

도움말은 clap이 파싱 중 출력하므로 번역된 명령 트리를 만든 뒤 그 트리로 파싱한다. 제품 코드는 `Cli::command()` 대신 `help_i18n::command()`를 사용한다. 본체에서는 `localized_command`라는 이름으로 제공한다.

영어 원본은 소스의 doc comment다. `lang/en.toml`은 컴파일된 영어 문구와 같아야 하며, host의 모든 도움말 항목을 내장 언어 파일 모두에 둔다. 도움말 항목 집합과 영어 값은 테스트가 대조한다. 사용자 언어팩에 일부만 있으면 영어로 폴백한다.

| 자리 | 키 |
|---|---|
| 루트 설명 | `cli.help._root.about` |
| 하위 명령 설명 | `cli.help._root.<a>.<b>.about` |
| 긴 설명 | 같은 경로의 `.long` |
| 인자 설명 | `cli.help._root.<a>.arg.<인자 id>.help` |
| 인자 긴 설명 | 같은 경로의 `.long` |

clap의 긴 설명은 doc comment에 빈 줄이 있을 때 생긴다. 여러 줄이라는 이유만으로 `.long` 키를 만들지 않는다. `every_english_help_key_names_a_real_slot`으로 실제 항목을, `every_english_help_value_matches_the_compiled_text`로 컴파일된 문구를 확인한다. `.about`·`.long`·`.help`를 마지막에 붙이는 것은 TOML의 한 키가 문자열과 하위 테이블을 동시에 가질 수 없기 때문이다.

한국어 UI 용어는 [공통 용어집](../concepts/ubiquitous-language.md)을 따른다. 도움말도 사용자 문구이므로 개발 문서의 약칭을 가져오지 않는다.

루트·`agent`·plugin 도움말의 그룹 제목(`cli.help_group.*`)과 루트 시작 안내(`cli.help_start.*`)는 clap 슬롯 밖의 문구다. `help_groups::text_keys`가 키 목록을 내고 `group_headings_and_start_lines_exist_in_every_language`가 내장 언어 파일을 모두 대조한다.

`help_frame`은 제목·help/version 설명·기본값·허용값 안내를 번역한다. 생성된 `help help` 트리에도 적용하며, 인자 설명이 없어도 기본값·허용값 안내는 표시한다. 영어는 clap 기본 템플릿을 사용한다. 단, 목적별 그룹을 표시하는 명령(루트, `agent`, 내부 연동 하위 명령이 있는 plugin 명령)은 언어와 관계없이 `help_groups`가 정한 템플릿을 쓴다([도움말 표시 계약](cli-structure.md#도움말-표시-계약)). 명령 이름·플래그·인자 ID·허용값 토큰은 번역하지 않는다.

허용값 토큰만 나열한 도움말도 입력값을 그대로 유지한다. 예를 들어
`codex.cli.arg.managed_args.action.help`는 managed CLI가 받는 액션 이름 목록이므로
번역 언어 파일에도 영어와 같은 값을 둔다. 이런 키는 `SAME_AS_ENGLISH_ALLOWLIST`에 키·언어·사유를
개별 등록한다. 토큰을 설명하는 자연어 문장은 번역한다.

파싱 오류는 `help_error`가 `ErrorKind`·`ContextKind`를 보고 번역한다. 실제 입력과 추천 값은 유지하며 하위 파서 `Error::source` 원문은 `Parser detail`에 남긴다. clap 밖에서 main으로 반환된 오류의 `Error:` 접두는 Rust Termination 출력이다. 그 안의 제품 문구는 번역하지만 서버의 JSON-RPC `error.message`는 CLI에서 치환하지 않는다.

플러그인 도움말은 discovery가 설치 자산의 `lang_dir`과 ID로 공용 `plugin_catalog::load`를 호출한다. 별도 프로세스를 띄우지 않고 설치 영어→실제 적용 언어→사용자 파일을 읽는다. `description_i18n_key`와 선택적 `help_i18n_key`가 없거나 번역이 누락되면 기존 description/help를 유지한다.

새 명령이나 clap 업그레이드 때 도움말과 대표 오류 fixture를 확인한다. 새 오류 종류는 공통 파싱 오류로 표시될 수 있다. 출력 문장 대신 종료 코드와 구조화된 응답으로 자동화한다.

### 하드코딩 허용 예외

번역하면 의미가 변하는 고유명사·고정 식별자는 허용:

- 수식키 이름(`Ctrl`/`Alt`/`Shift`/`Cmd`), 단축키 조합 표시(`Ctrl+Shift+P`)
- 폰트 프리뷰 텍스트(`AaBbCcDdEeFfGg`), 언어 이름 자체(`English`/`한국어`/`日本語`/`简体中文`)
- 내부 진단 `tracing::*` 로그(사용자 표면 아님)
- `clap` 파생 매크로의 `about`/`help` 는 **더 이상 하드코딩 예외가 아니다** — 도움말은
  실행 시점에 번역된다(아래 "CLI 도움말" 절). doc comment 는 그대로 두되 **영어로만**
  쓴다: 그것이 영어 원본이고, `clap_help_text_is_english_only` 가 이 규칙을 검사한다.
  개발자용 배경 설명(설계 근거, 원칙 번호 인용 등)은 help 가 아니라 `//` 주석이나
  `docs/` 에 둔다 ([`cli-structure.md`](cli-structure.md) "도움말 문구").
- CLI 가 host 의 에러 응답을 중계하는 `Error (…)` 줄과 그 아래 `data: …` 줄
  (`crates/tasty-cli/src/rpc_error.rs`) — 본문은 host 가 만든 문구와 `error.data` 를 그대로
  통과시키고 접두 `Error (` · `data: ` 는 그 응답 형식의 일부다
- `crates/tasty-cli/src/out.rs` 의 `StdoutClosed` Display(`stdout closed by reader`) —
  사용자 표면에 닿지 않는다. CLI 진입점이 `quiet_if_stdout_closed` 로 종료 코드 0 으로
  접어 아무것도 출력하지 않는다(docs/dev-guide/cli-structure.md). 그 외 stdout 쓰기 실패는 `cli.out.write_failed`
- `format.rs` 밖의 **기계 판독 구조 출력** — attach mirror-dump 의 섹션 헤더
  (`crates/tasty-cli/src/local/attach.rs` 의 `=== surface N ===`, grep 로 구획을 자른다)와
  hook 실패 기록의 `key=value` 한 줄(`hook_failure.rs`, `grep`/`awk` 로 읽는 레코드).
  구획자가 로케일에 따라 흔들리면 그 출력을 소비하는 쪽이 깨진다.
  **`hook-failures.log` 의 로케일 무관성은 구획자와 구조화된 필드(`method`/`event`/`surface`/
  `code`)로 유지한다** ([CLI 크레이트 내부 구조 — 세 갈래 대칭](cli-structure.md)).
  `reason` 산문은 그 문구를 **만든 쪽**의 언어를 따른다 — CLI 가 만드는 두 갈래는 영어이고,
  답한 쪽이 만든 문구를 그대로 싣는 갈래는 그 쪽의 언어다. 앞엣것을 영어로 묶는 이유는 —
  셸 래퍼가 `|| true` 로 exit code 를 버려 이 파일이 hook 전달 실패의 유일한 흔적이고,
  읽는 주체가 에이전트일 수 있어 알려진 실패 패턴과 대조 가능해야 한다. 같은 실패의
  **stderr 는 번역문**을 유지한다(사용자 표면). 그 분리는 `hook_failure::record` 가
  `DiagnosticEnglish` 만 받는 것으로 타입이 지키고, 그 타입의 탈출구
  (`new_unchecked`)는 `crates/tasty-doc-guards/tests/hook_failure_reason_stays_english.rs` 가 소스 스캔으로 막는다.
  **그 스캔의 술어는 둘이고 서로를 못 대신한다** — 하나는 인자의 **출처**를 보고(`t()` 계열
  호출이나 번역 래퍼가 섞였나), 다른 하나는 인자에 박힌 리터럴의 **값**을 본다(한글·가나·한자가
  들어 있으면 어떤 로케일에서도 영어가 아니다). 출처 검사만 있을 때 `t()` 를 안 거치고 소스에
  직접 박은 한국어 리터럴이 그대로 통과했다. 값 검사도 규약 전체는 못 잰다 — ASCII 로만 된
  번역문(스페인어 등)은 값으로 구별되지 않고, 그 갈래는 출처 검사가 받는다.
  **그 타입과 가드가 덮는 것은 CLI 가 문구를 만드는 두 갈래뿐이다** — 셋째(오류 응답)의
  문구는 답한 쪽이 자기 프로세스에서 만들어 넘기므로 CLI 소스에 볼 `t()` 가 없다.
  스캔 범위를 넓히는 문제가 아니라 문구의 생산지가 프로세스 밖이라는 문제다. 그래서 그
  응답은 번역될 수 있는 reason 문구 대신 code 필드로 분류한다. 오류 코드의 뜻은
  로케일에 따라 바뀌지 않는다.
- **debug 전용 명령**(`#![cfg(debug_assertions)]`)의 진행 출력 — `local/debug.rs` 의
  `stream-echo` 진행 줄. release 표면에 존재하지 않고 에이전트 자기검증용이라
  내부 진단 로그와 같은 자리다([debug-ipc.md](debug-ipc.md))
- JSON-RPC method 이름·프로토콜 토큰
- `tasty list` 계열(`workspaces`/`tree`/`panes`)의 구조 출력이 쓰는 고정 토큰 —
  `(id:N)`/`[mirror]`/`(N panes)`/`[ws:N name]`, 그리고 같은 파일의 구조 출력
  (`agent task-list`·알림 목록)이 쓰는 **빈 상태 토큰**(`No tasks`/`No notifications`).
  한 행 안에서 기계 파싱 대상과 나란히 놓이는
  식별자라, 이 중 하나만 번역되면 그 행 자체가 로케일에 따라 흔들리고, 빈 상태
  토큰이 바뀌면 그 출력을 파이프로 소비하는 에이전트가 깨진다
  (`crates/tasty-cli/src/format.rs` 의 `format_workspace_list` 등 — 이 파일은
  `t()` 호출이 없는 것이 기존 컨벤션이다)
- **매니페스트·설정 키를 그대로 비추는 필드명 행** — `tasty plugin doctor` 의
  `name:`/`version:`/`manifest_version:`/`api_version:` 와 action 요약의
  `surface "…"`/`ipc "…"`(매니페스트 `kind` 값)·handler 행의 `detector`
  (`crates/tasty-cli/src/plugin.rs`), `tasty tool remote-profile show` 의
  `ssh_ref`/`remote_tasty`/`port_mode`/`extra_options` 등 프로필 TOML 키 행과
  `tasty tool passkey show` 의 `name`/`kind`/`value` 행(`local/remote_profile.rs`,
  `local/passkey.rs`). 사용자가 그 단어로 매니페스트·설정 파일을 찾아가는 식별자라
  번역하면 대응이 끊긴다. 같은 출력의 문장·라벨(`Detectors contributed: N`,
  `(no action)` 등)은 `cli.plugin.*` 키다

그 외 사람이 읽는 모든 문자열은 예외 없이 `t()`.

### 위젯 호출이 아닌 경로도 대상이다

`t()` 의 적용 범위는 egui 위젯 인자에 한정되지 않는다. 다음처럼 *위젯 호출 형태가 아닌* 경로로 사람에게 도달하는 문자열도 전부 `t()` 다:

| 형태 | 예 | 키 |
|------|-----|-----|
| 도메인 intent 필드 초기화 | 터미널 BEL 알림의 `DomainIntent::PushNotification { title }` | `notification.bell_title` |
| IPC 파라미터 생략 시 UI 로 흘러가는 기본값 | `notification.create` 의 `title` 생략 | `notification.default_title` |
| `unwrap_or(..)` 폴백 라벨 | 알림 패널의 사라진 출처 워크스페이스명 · 원격 attach mirror 탭 제목 | `notification_panel.unknown_workspace` · `attach.tab_title_fallback` |

`notification.create`의 제목은 선택 사항이다. 생략하면 호스트가 번역된 기본 제목을 넣는다. CLI `tasty notify`도 `--title`이 없으면 자체 문구를 채우지 않고 생략 또는 null로 전달한다. 기본 제목을 정하는 곳은 호스트 하나다.

같은 값이 **기계 식별에도** 쓰인다면 표시 문자열과 식별 필드를 분리한다 — 알림은 `source` / `HookEvent` 로 식별하고 제목은 번역한다. 제목 문자열 비교로 분기하는 소비자를 만들지 않는다(이 문서).

## 공용 위젯의 문자열 — 호출자 주입

`crates/tasty-ui-widgets` 는 `tasty-i18n` 을 **의존하지 않는다**(egui / egui_extras / tasty-icons /
tasty-egui-theme / tasty-type-* 만). 위젯은 번역 테이블에 접근할 수 없으므로 **자기 문구를
소유할 수 없다** — 문구가 필요한 위젯은 호출자가 `t()` / `t_fmt()` 로 만든 문자열을 파라미터로
주입받고, 위젯은 *어느 문구를 쓸지 고르는 판정*만 한다.

선례: `multi_select` 의 트리거 요약 라벨, `SearchableSelect` 의 `SearchableSelectLabels`(값이 없을 때의 트리거 문구 · 검색칸 안내 · 결과 없음 · 로딩 행). 옵션 문구는 `SearchableSelectOption::label` 로 함께 넘어오며, 고정 행(예: 기본 글꼴)의 문구도 호출자가 번역해 넣는다.

같은 원칙이 `tasty-i18n` 을 의존하지 않는 **다른 leaf 크레이트**에도 적용된다 — 예: `tasty-git-core`(host 와
git-viewer plugin 이 공유하는 데이터 크레이트, [원격 attach (Remote attach)](../features/remote-attach/index.md)).
데이터 크레이트는 "값이 없음"을 빈 문자열/`Option` 으로 돌려주고, 그 자리에 보여줄 문구(메시지 없는 커밋·작성자
미상 등)는 **소비자**가 고른다 — plugin 은 자기 `Translator`(git-viewer: `git_viewer.no_message` /
`git_viewer.unknown_author`), host 는 `t()`. 원격 attach 경로에서는 결과를
만드는 host 가 아니라 받아서 그리는 plugin 이 표시 주체이므로, host 측에서 문구를 채우면 원격 인스턴스의 언어가
로컬 화면에 새어 들어온다(이 문서).

전송 계층도 같다 — `crates/tasty-ipc` 는 wire framing / 세션 크레이트라 `tasty-i18n` 을 의존하지 않는다.
실패는 **조건을 담은 타입**으로 돌려주고(`port_file::PortFileError` — `HomeUnresolved` / `NotFound { path }` /
`Invalid`), 그 조건을 현재 로케일 문장으로 바꾸는 곳은 CLI 한 곳이다(`tasty_cli::port_file::read_port`,
`cli.port_file.*`). 포트 파일 조회는 CLI 의 여러 명령에서 일어나므로 지점마다 문구를 만들면 같은 실패가
명령에 따라 다르게 읽힌다 — 조회를 그 함수 하나로 모아 문구를 단일화한다. `PortFileError` 의 `Display` 는
이 경로를 타지 않는 소비자를 위한 **영어 기본 렌더링**이며 `lang/en.toml` 값과 문자 단위로 같아야 한다
(정합은 `tasty-cli` 테스트가 강제한다 — 갈라지면 같은 실패가 영어로도 두 가지로 읽힌다).

```rust
// 호출자(본체) — 번역은 여기서
let labels = MultiSelectLabels {
    none: t("dag_list.filter_none"),
    some: t("dag_list.filter_some"),   // "{} selected" — 치환 자리는 위젯이 채운다
    some_one: t_count_template("dag_list.filter_some", 1), // 하나만 골랐을 때(단수 규칙)
    all:  t("dag_list.filter_all"),
};
multi_select(
    ui, theme, "dag_status", &mut selected, &opts,
    None,      // 행 단위 disabled 마스크 — 없으면 전부 활성
    &labels,
    None,      // 일괄 토글 행 opt-in — 켜면 문구 2 개도 같이 주입한다(아래)
    width, true,
);
```

일괄 토글 행을 켜는 호출부는 문구를 **같은 방식으로** 주입한다 — "켬" 과 "문구" 가
한 값이라 어긋날 수 없다.

```rust
let all_toggle = MultiSelectAllToggle {
    select_all: t("some_screen.select_all"),
    clear_all:  t("some_screen.clear_all"),
};
// … multi_select(…, &labels, Some(all_toggle), width, true)
```

- 치환 규약은 본체 `t_fmt` 와 같은 `{}` — 위젯이 `replacen("{}", …, 1)` 로 한 번만 채운다.
  호출자는 `t_fmt` 로 미리 채우지 말고 **`{}` 가 남은 원문**을 넘긴다(개수를 아는 건 위젯이다).
- 갤러리 specimen 은 본체가 아니라 카탈로그라 시안의 데모 값과 짧은 라벨은 영어 리터럴로 주입한다.
  본체 문구를 옮긴 문장·안내문(20자 이상이며 같은 값을 가진 키가 하나인 사본)은 사본을 두지 않고 갤러리가
  `tasty_gallery::i18n::t()`·`t_fmt()`·`t_fmt2()` 로 읽는다. macOS 권한 안내 본문(`macos_permissions.notice.*`
  문단, 조립은 `tasty_platform::macos_permission_notice`)과 HTML 스크립트 배너·탭 표지 문안
  (`banner.html_script.*`)도 같다. attach 대기 안내의 단수·복수 문장, 요청 종류와 선행 배치의
  새 탭 표지도 본체의 `attach.pending.*` 키를 읽는다. 경과 시간과 카탈로그 제목은 견본 값이다.
  Preset 도구줄의 저장 방식 안내도 본체와 같은 `preset.toolbar.saved` 키를 읽는다.
  이 안내는 자동 저장 모드를 뜻하며 개별 파일 저장의 receipt 성공 표시는 아니다.
  `const` 표 안처럼 함수를 부를 수 없는 자리의 사본은 리터럴로 남고
  아래 기준 파일이 지킨다. `t()`는 처음 부를 때 `tasty_i18n::init("en")` 을 한 번 한다. 이 초기화도
  본체와 같이 사용자 홈의 덮어쓰기 파일(`<TASTY_HOME, 없으면 debug 빌드는 ~/.tasty-debug · release
  빌드는 ~/.tasty>/lang/en.toml`)을 내장 영어 위에 얹으므로, 그 파일이 있으면 갤러리 표시도 영향을
  받는다. 갤러리는 보통 debug 빌드(`cargo run -p tasty-gallery`)로 실행하므로 `TASTY_HOME` 이 없으면
  `~/.tasty-debug/lang/en.toml` 이 읽힌다.
  한 화면에 언어를 나란히 보이는 예제(탐색기 결과 카드의 남은 임시 폴더 카드 등)는
  `tasty_gallery::i18n::t_lang(code, key)` 로 ko·ja·zh-Hans 문자열을 읽는다. 저장소의 `lang/ko.toml`·`lang/ja.toml`·`lang/zh-Hans.toml` 을
  빌드에 넣어 펼치며 사용자 덮어쓰기 파일은 읽지 않는다. 키가 없거나 code 가 내장 언어가 아니면 영어로 돌아간다.
  자리 채우기는 `tasty_i18n::fill_args` 다.
- 갤러리에 리터럴로 남은 lang 문구 사본은 `crates/tasty-gallery/tests/lang_copies.rs` 가 지킨다. 이 시험은
  갤러리 `src/` 의 문자열 리터럴 가운데 `lang/en.toml` 값(`meta.*` 제외)과 글자 단위로 같은 것을 모아
  기준 파일 `crates/tasty-gallery/tests/lang_copies.txt`(경로·리터럴·같은 값을 가진 키) 와 비교한다.
  새 리터럴이 lang 값과 같아지거나(새 손 사본) 기준의 사본이 lang 값과 더는 같지 않으면(lang 문구를
  바꿨거나 갤러리 문구를 바꿨다) 실패한다. 갤러리 문구를 고치거나 `t()` 로 바꾼 뒤
  `TASTY_GALLERY_LANG_COPIES_WRITE=1 cargo test -p tasty-gallery --test lang_copies` 로 기준을 다시 쓴다.
  기준을 다시 쓴 뒤에는 기준에서 빠진 줄마다 그 리터럴이 낡은 사본으로 남지 않았는지 확인한다.
  우연히 같은 짧은 낱말(예: `—`, `Ctrl`)도 기준에 들어가므로, 그 lang 값을 바꾸면 이 시험이 갤러리
  쪽을 확인하라고 실패한다. 리터럴 추출은 주석·문자 리터럴·바이트 문자열을 건너뛰고 일반·raw 문자열만
  읽으며, `format!` 등으로 조립한 문구와 `concat!` 조각은 하나의 리터럴로 보지 않는다.

## 강제 테스트

아래 표의 가드 테스트가 위 규칙을 집행한다(채널은 [`ci-gates.md`](ci-gates.md) 가 정본이다).
pre-commit hook 은 이 가드들을 돌리지 않는다(hook 목록은 [`git-hooks.md`](git-hooks.md)).
그러므로 번역 문자열을 건드린 작업은 커밋 전에 아래 명령을 **직접** 돌린다.

```bash
cargo test --locked --test i18n_key_parity
cargo test --locked -p tasty-doc-guards --test no_hardcoded_ui_strings
```

내장 언어 목록을 바꾼 작업은 `cargo test --locked --test i18n_language_lists`와

인자(변수·`format!`)와 `anyhow!`/`bail!` 메시지 — 변수에 담긴 영어 문장과 anyhow 에러 문구는 잡지
못하므로 리뷰가 남는 몫이다. 값 형태로 자동 예외되는 것(기호·숫자만인 값, 다섯 자 이하 약어, 경로·URL·
`tasty …` 명령, 소문자 단일 단어 폴백)도 등록이 필요 없다.

**잔존 위반의 처리** — 두 테스트는 `PENDING_FIX_*` 상수에 알려진 위반을 파일·리터럴(또는 키)·
고칠 방법과 함께 둔다. 그 항목이 사라지면(=고쳐지면) 목록에서 지우라고 fail 하므로 빚이 조용히
남지 않는다. 새 위반을 여기 넣어 덮지 않는다 — 고치는 것이 기본이다.
